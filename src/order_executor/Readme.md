# The overall flow

```text
Kafka signal arrives
        ↓
consumer.py reads it, creates an Order object (status=PENDING)
        ↓
Risk Manager  ← "approve or reject this order?"
        ↓ approved
Order Manager ← "track this order's lifecycle"
        ↓
Broker Adapter (PaperAdapter or FyersAdapter)  ← "actually execute it"
        ↓
Order status updated (FILLED / REJECTED)
        ↓
Publish result back to Kafka
```



## Risk Manager 

Answers "should we place this order?" before touching the broker. Examples of checks:

Already holding AAPL? Don't buy more (max position limit)
Lost $500 today already? Stop trading for today (daily loss limit)
Same signal fired twice in 10 seconds? Ignore the second one (duplicate guard)
Order size too large for account balance? Reject
It's a pre-trade guardrail. Without it, a bug in your signal generator can blow up your account in minutes. Every real firm has this.



Idempotency — the hard one. Imagine this sequence:

1. You call Fyers API: "Place BUY order for AAPL"
2. Network drops
3. You never got a confirmation
4. Question: was the order placed or not?

If you retry blindly, you might place the order TWICE — now you're holding 2x the position you wanted. The fix: every order gets a unique client_order_id generated by YOU before sending. When you retry, you send the same client_order_id. The broker deduplicates on their end — if they already have that ID, they return the existing order instead of creating a new one. This is idempotency.


## 

Circuit Breaker — borrowed from electrical engineering. If something goes wrong repeatedly, stop automatically instead of keep failing:

Fyers API returned error 3 times in a row?
→ Stop placing orders for 60 seconds
→ Alert / log
→ Try again after cooldown

Without this, a broken API connection causes your system to spam error requests in a tight loop, potentially getting your account rate-limited or IP blocked.


Position Reconciliation — your internal state vs broker's actual state may drift. Example:

Your system thinks: AAPL position = 10 shares
Fyers actually shows: AAPL position = 8 shares (maybe 2 were sold by a manual trade you did)

Reconciliation = periodically query the broker for actual positions and sync your internal state. Typically done at startup and every few minutes. Critical for not overselling or overbuying.

Slippage Modelling — when you send a market order for AAPL at $150.00, you rarely get $150.00. You might get $150.03 because the market moved in the milliseconds between your signal and fill. That $0.03 difference is slippage. In paper trading, you simulate this by adding a small random offset to the fill price so your paper results are realistic, not optimistic.
